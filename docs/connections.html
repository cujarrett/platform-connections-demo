Platform-Managed Connections

How one service call is gated — and where each gate lives.

Today any pod can call anything.
Goal: a call works only if it was declared.

Every gate below is rendered by the Crossplane Api/Spa composition and enforced by the Envoy sidecar. App teams add a field to a YAML they already own. No app code changes, ever.

1The journey of one call

Five gates, five layers. Click any gate.

2The handshake — why "registered" is physics, not paperwork

Istio gates the call twice: once leaving downstream, once entering upstream. Two pods, two namespaces, two teams.

downstream team declares

consumes

"I intend to call this."
Renders the Sidecar egress entry (+ ServiceEntry if off-platform).
Enforced at the downstream app's outbound sidecar.

AND
upstream team declares

provides

"I accept calls from this."
Renders the AuthorizationPolicy.
Enforced at the upstream app's inbound sidecar.

both declared → call works downstream only → upstream's sidecar returns 403 upstream only → downstream's own sidecar refuses to send neither → nothing leaves the pod

Neither team can create an edge alone. Neither team can be surprised by one. Upstream consent and downstream intent, each with its own git history and its own CODEOWNERS — with no workflow engine and no new controller. Off-platform destinations work the same way: a central catalog entry is the upstream consent, and the platform team is the upstream side.

What the app teams actually write

# my-vinyl-api.yaml — the UPSTREAM APP
spec:
  parameters:
    owningRole: "my-vinyl.approver"       # Entra app role that approves this API's downstream apps
    provides:
      - name: collection                  # the named interface downstream apps subscribe to
        methods: [GET]
        paths: ["/api/v1/collection/*"]
        allowedDownstream:
          - { namespace: my-vinyl, app: my-vinyl-spa }

# my-vinyl-spa.yaml — the DOWNSTREAM APP
spec:
  parameters:
    consumes:
      - { platform: my-vinyl-api, interface: collection }
      - { external: discogs }             # catalog key, not a hostname

No hostnames, no ports, no SPIFFE strings, no Istio kinds. Named interfaces, not a flat downstream list — one API's /public/* and /admin/* must not share a grant, and "who consumes collection?" becomes a one-line query.

3The safety dial — how a namespace crosses over

One field, connectionPosture. Default off renders nothing at all.

rung 0 · today

off

Permissive mTLS, ALLOW_ANY egress. Nothing declared, nothing denied. Composition renders zero objects.

rung 1

baseline

Infra allows rendered first — DNS, Prometheus, Traefik, kubelet probes, same-namespace traffic. Still not enforced, so nothing can break.

rung 2 · the work

observe

Declarations render as dry-run. Traffic flows untouched while a counter records what enforcement would block.

rung 3 · the goal

enforce

STRICT mTLS + live authz + REGISTRY_ONLY. Undeclared is denied. This is the control.

The rule: never enforce until the dry-run says nothing breaks. observe is the work; enforce is a non-event. Exit criteria: zero would-be denials for 7 consecutive days, covering at least one full weekly batch cycle. Break-glass is one field back to off — ArgoCD prunes it.

Reading the dry-run counter

kubectl exec -n <ns> deploy/<app> -c istio-proxy \
  -- pilot-agent request GET stats | grep rbac.*shadow

  http.inbound_0.0.0.0_8080.rbac.shadow_allowed: 4812
  http.inbound_0.0.0.0_8080.rbac.shadow_denied:     3   # <-- must reach 0 before enforce
The trap that already bit this cluster: an ALLOW AuthorizationPolicy is default-deny for the workload it selects, the instant it lands. Never render one into a namespace that isn't already baselined. And PeerAuthentication: STRICT has no dry-run — that is the cliff, which is why it appears only at enforce, last in sync-wave order.

4Three authorization questions — they stack, they don't substitute

Most confusion comes from collapsing these into one word.

QuestionSubjectLayerTechnologyApp code changes?
A Which workload is calling?a pod / service account L5-L6 mTLS → L7 policyIstio + SPIFFEno
B Which user, with what coarse role?a human, or an app acting for one L7Entra ID (OIDC) + Istiono — but the token must be propagated
C May that user do this action on this object?a (user, action, object) triple L7+OpenFGA / OPA / Cedar / SpiceDByes — or via ext_authz

Entra and OpenFGA are not alternatives — they are B and C. Entra can never answer C, because Entra has no idea what a vinyl record is. OpenFGA can never answer B, because it does not issue or verify tokens. And neither answers A — which is the question this work is actually about, and the one the mesh gives you for free.

The two-key rule — one policy, both facts

The mesh is the right home for coarse authz because it is the only place workload identity and user identity exist at the same moment.

rules:
  - from:
      - source:
          principals: ["cluster.local/ns/my-vinyl/sa/my-vinyl-spa"]   # A — proven workload
    to:
      - operation: { methods: [GET], paths: ["/api/v1/*"] }
    when:
      - key: request.auth.claims[roles]                               # B — proven user role
        values: ["collection.reader"]
Fails open if you get this wrong: RequestAuthentication alone authorizes nothing — it only says "a token, if present, must be valid." A request with no token sails straight through. You must also render an AuthorizationPolicy requiring requestPrincipals: ["*"]. This is the most common Istio security misconfiguration in production.

5Choosing a fine-grained engine (question C)

EngineModelBest whenCost of ownership
OpenFGA CNCF, ZanzibarReBAC — relationship tuples authz is about ownership, sharing, hierarchiesrun + scale a tuple store; keep tuples in sync with your data
SpiceDB AuthZedReBAC + consistency tokens same, but you need read-after-write guaranteeshigher; commercial support available
OPA / Styra CNCF, RegoABAC — policy over attributes rules are attribute-shaped; org already writes Regolowest to start; hard to answer "who can see X?"
Cedar / AVP AWSABAC + RBAC, formally verifiable AWS-centric, want policy analysismanaged, but couples authz to AWS
Entra ID aloneRBAC — roles, groups, scopes coarse tiers only: reader / writer / adminalready owned and paid for

Recommendation: neither, yet. Build the seam — Istio's action: CUSTOM pointing at a declared extensionProvider — and leave it unset everywhere. Istio's native claim/method/path matching covers a startling amount of what teams reach for OpenFGA to do. Reach for C only when a decision genuinely depends on which row. Then pick by shape: owned-and-shared objects → OpenFGA; attribute conditions → OPA.

The trap: ext_authz puts a synchronous network call in the request path of every request. Ship it without a cache, without a deliberate per-service fail-open/fail-closed decision, and without its own SLO and paging, and you have built an outage generator. The platform field therefore carries failOpen: false as a required, no-default value — the team must say it out loud.

6What this demo namespace proves

Two downstream instances. Identical image, identical code. Different ServiceAccount — that is the entire test.

Row 5 is the interesting one. The public API checks no identity itself — yet the mesh still controls which workload may reach it, because the block happens at the downstream app's own sidecar before the packet leaves the pod.

This namespace stays pinned at enforce permanently. It is the regression canary every composition change proves against first — the Api/Spa compositions are shared by every app on the platform, so their blast radius is the whole cluster.
